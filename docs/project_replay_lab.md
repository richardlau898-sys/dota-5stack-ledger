# 刀塔账房 大项目：录像实验室 + 车队成长周报

**一句话目标：** 每场车队比赛结束后，平台自动解析真录像，给出基于真实走位的复盘；每周一给五个人各一个具体的改进目标，并跟踪下周有没有做到。

这是一个多里程碑的大项目（M0–M4），每个里程碑结束都有 Richard 的检查点。仓库里 `AGENTS.md` 的全部规则（第 1–24 条）照常适用，第五节另有本项目的专用规则。

---

## 一、为什么做这个

**1. 现在答不了最有用的问题。** 平台现在的数据全部来自 OpenDota 的解析结果，我在仓库样本里逐项确认过，有这些：

- 每分钟的经济、经验、补刀曲线。
- 击杀、阵亡、购买、买活、符文的时间。
- 眼位的放置和消失坐标（`obs_log`、`obs_left_log`）。
- 团战里的阵亡坐标（`teamfights[].players[].deaths_pos`）。
- 前 10 分钟的走位热力图（`lane_pos`）。

**没有整局的逐秒位置。** 所以第一版的"逐秒小地图"只能靠合成，"在哪里被抓""当时有没有视野""队友离多远"这类问题答不了，第二、三轮修复时只能把这些说法删掉。

**2. 录像文件里有这些数据。** 22 份样本里 21 份带 `replay_url`（格式为 `http://replay<N>.valve.net/570/<比赛号>_<salt>.dem.bz2`）。OpenDota 自己就是用开源解析器从录像里提取数据的。录像在 Valve 服务器上只保留一段时间，所以必须在赛后尽快下载。

**3. 单场复盘不会自动变成习惯。** 想变强，需要"本周盯一件事，下周看有没有做到"。现在平台只有单场复盘，没有这个闭环。

---

## 二、项目完成时的样子

1. 车队打完一场，比赛结束后 1 小时内（目标值，以 M0 实测为准），录像被自动下载、解析、入库，失败了在网站上看得到原因。
2. 小地图显示真实走位，可以按秒拖动；没有录像数据的比赛照旧显示"示意位置"。
3. 新增一组基于位置的实测指标，每一条都能拿比赛号和时间点到游戏客户端里核对。比如：阵亡时最近的队友有多远、阵亡点有没有我方视野、开雾路线和结果、TP 从按下到参战用了多久。
4. 每周一自动生成车队周报：每人 3 条和自己过去 4 周对比的趋势、1 个下周目标，以及上周目标完成了没有。网站上能看，也推送到群里。

## 三、范围外（这次不做）

- 比赛进行中的实时分析。
- 职业比赛、路人对手的分析。
- 需要队友登录 Steam 或授权的任何功能。
- 新增 LLM 调用。周报用规则生成；要不要用 AI 润色，以后再议。
- 付费服务器。如果 M0 证明 GitHub Actions 跑不动，再单独讨论。

## 四、里程碑

### M0 · 可行性实测（必须先做；只交报告和脚本，不改产品代码）

这一步上次（F9）被写成了"实测"但其实没跑。这次每个数字都必须出自真实运行的输出。

- **取样：** 3 场车队最近的比赛，开赛时间都在 3 天以内，其中至少 1 场是当前最新补丁。
- **下载与解析：** 下载 `replay_url`、解压，用 OpenDota 的开源解析器 `odota/parser`（或它底层的 Java 解析库 clarity）解析。用 Docker 镜像还是从源码构建，自己选，报告里写清楚。
- **记录这些：**
  - 每一步的命令和输出原文。
  - 耗时。
  - 文件大小：压缩录像、解压后、解析输出、再压缩后。
  - 输出里有哪些事件类型、每类多少条。
- **确认有没有逐秒位置：** 据我所知，解析器会输出每名玩家按时间采样的坐标，但字段名、采样频率、坐标系都要实测确认。
  - 用同一场比赛核对：解析出的阵亡时位置，与 OpenDota 已有的团战阵亡坐标 `deaths_pos` 是否对得上；眼位坐标与 `obs_log` 是否对得上。
  - 确认不了就写"确认不了"，然后停下。
- **录像保留期：** 对开赛 1、3、7、10、14、21 天前的车队比赛，各请求一次 `replay_url`（只发 HEAD 请求），记录状态码。由此得出最晚要在赛后多久之内下载。
- **运行环境：** 在 GitHub Actions 上实际跑一次，记录耗时和内存峰值。仓库是公开的，Actions 日志所有人可见，日志里不得打印玩家名、比赛数据或解析结果。
- **存储估算：** 按每周车队比赛场数（从近 4 周的历史里数出来）估算每月存储量，对照 Supabase 当前套餐的实际额度（去后台看，写出数字和截图）。
- **交付：**
  - `docs/m0_replay_feasibility.md`。
  - `tools/replay_lab/` 下的脚本。
  - 一份真实解析输出的截取样本，不超过 200 行，注明来自哪场比赛。
- **验收：** 报告里每一个数字，都能在同一份报告附带的命令输出里找到。
- **Richard 检查点：**
  - 读报告，决定 D11–D13，以及是否继续 M1–M3。
  - 如果录像下载不到、解析失败或者没有坐标：M1–M3 取消，直接做 M4。M4 不依赖录像。

### M1 · 解析管线

- **触发方式：**
  - 手动输入比赛号。
  - 自动检测花名册成员的新比赛（复用赛后推送里的检测逻辑），检测频率按 M0 得出的保留期定。
- **流程：** 下载 → 解析 → 降采样 → 压缩 → 上传 Supabase Storage（`replays/<比赛号>/timeline.json.gz`）。
- **状态表 `replay_jobs`：** 记录每场比赛处于哪一步：排队、下载中、解析中、完成、失败、录像已过期，以及错误码和各步耗时。
- **数据格式：** 写成 `docs/replay_timeline_schema.md`，带版本号。位置的采样频率按 M0 的结果和存储预算定。
- **可靠性：**
  - 重复运行同一场不会重复处理。
  - 下载失败带退避重试。
  - 每一步有超时。
  - 同时只处理有限几场。
  - 只处理至少有一名花名册成员的比赛。
- **网站：** 比赛页显示录像状态，比如"录像解析中""录像已过期，无法获取真实走位"。
- **测试：** 用 M0 那份真实截取样本，不得用合成数据。
- **验收：** 连续运行 7 天，贴出 `replay_jobs` 表的统计：处理了几场、成功、过期、失败各几场、平均耗时。失败的逐场说明原因。
- **Richard 检查点：** 看统计，确认成功率能接受。

### M2 · 真实小地图与时间轴

- **展示：**
  - 有录像数据的比赛：小地图显示真实位置，不再用合成位置。
  - 没有录像数据的比赛：照旧显示，并保留"示意位置"标注。
  - 阵亡标记、眼位（真实存活时间）、开雾路线叠加在小地图上。
- **加载：** 时间轴数据按需加载，切到这个标签页时才下载。单场的传输大小上限在 M1 之后定（根据实测结果写进设计）。
- **验收：**
  - **自动检查：** 3 场比赛里，所有团战阵亡时刻的解析位置，与 OpenDota 的 `deaths_pos` 误差在设计里定的范围内。
  - **人工检查：** 给出 5 个"比赛号 + 时间点 + 应该看到什么"，Richard 在游戏客户端里打开同场录像核对，通过才合并。
  - 桌面和手机截图上传到 PR。

### M3 · 基于位置的实测分析

用真实位置，把第二、三轮里只能删掉或标为"推断"的那些说法，重新做成实测：

| 指标 | 定义要点 |
|---|---|
| 阵亡时最近队友距离 | 阵亡那一刻，最近一名存活队友的距离；同时给出 1200 码内有几名队友（距离阈值写成常量并注明来源） |
| 阵亡点视野 | 阵亡点是否在我方存活眼位的视野内。视野半径必须来自游戏常量文件或可引用的来源，不得凭记忆写 |
| 团战外阵亡的来路 | 击杀者从哪个方向来；死前 10 秒自己所在位置有没有我方视野 |
| 开雾 | 真实开雾的时间、位置、移动路线；之后 60 秒内的击杀和阵亡 |
| TP 支援 | 从按下 TP 到落地、再到第一次造成伤害的时间；落点离团战中心的距离 |
| 团战站位 | 开团时刻五人之间的平均距离；先手方是谁 |
| 视野覆盖 | 每分钟我方假眼覆盖关键区域的比例。区域写成数据文件（多边形坐标），附在设计里给 Richard 看 |

- **每个指标都要有：**
  - 定义文档，包括用了哪些字段、阈值和阈值来源。
  - 3 场真实比赛的计算结果。
  - 5 个能在客户端核对的例子。
  - 证据标签为"实测"，并注明来源字段。
  - 措辞遵守教练模式词表。
- **加锅：** 这些指标进入复盘正文和"下一把 3 件事"的候选。要不要计入分锅，先在设计里写方案，Richard 批准后再做。
- **验收：** Richard 抽查例子，全部核对通过才合并。每个指标一个 PR。

### M4 · 车队成长周报与目标（不依赖 M1–M3，可以和 M1 并行）

- **数据：**
  - 已复盘的比赛。
  - 全量历史（`tools/sync_full_match_history.py`，需要 Richard 用自己的环境跑一次同步）。
  - 有录像数据的比赛，加上 M3 的指标。
- **内容（每周一生成上一周的）：**
  - **车队：** 场数、胜率、5 人黑和非 5 人黑分开；3 个团队指标的走势（比如赢团后的推进转化、第一个肉山时间、领先被翻盘的次数）。
  - **每人：**
    - 3 条和自己过去 4 周对比的趋势，只用"实测"数据，样本不足就写"样本不足"。
    - 1 个下周目标的建议。
    - 上周目标完成了没有。
- **目标：** 由系统建议，本人或 Richard 在网页上确认后才生效（D14）。没确认的不跟踪。
- **送达：** 网站上的周报页面，以及推送到群里（D5）。推送失败时如实报告，不得重复发送。
- **语气：** 只用教练模式。
- **验收：**
  - 用上一周的真实数据生成一份周报，给 Richard 看。
  - 连续两周自动运行成功。
  - 目标进度的计算有测试覆盖，含样本不足、没有目标、目标达成三种情况。

## 五、本项目的专用规则

1. **先设计，后代码。** 每个里程碑开工前交一页设计，Richard 在 PR 里明确批准后才写代码。设计里写清楚：数据从哪来、存哪、格式、阈值和来源、成本、失败时用户看到什么。
2. **PR 要小。** 每个 PR 的代码改动控制在 500 行左右（数据文件和真实样本不算）。一个里程碑可以有多个 PR。
3. **里程碑报告。** 每个里程碑结束时交一份：做了什么、实测数字、没做到的、下一步建议。
4. **公开仓库的保密要求。** 提交、Actions 日志、artifact 里不得出现玩家数据、录像文件或解析结果。全部走 Supabase，凭据放在 GitHub Secrets。
5. **游戏常数要有来源。** 视野半径、技能距离、TP 时间这类数值，写进一个常量文件，每个数值注明来源（游戏数据文件、可引用的文档或实测）。不得凭记忆写。查不到就停下来问。
6. **预估不能写成实测。** 标题或表格写"实测"的数字，必须附命令和原始输出。没跑过的写"预估"，并说明怎么估的。
7. **不新增费用。** 只用 GitHub Actions（公开仓库免费）和现有的 Supabase。任何需要付费的方案，先写进里程碑报告让 Richard 决定。
8. **做完一个里程碑就停下，等检查点。**

## 七、风险与退路

| 风险 | 退路 |
|---|---|
| 录像过期太快，赶不上下载 | 加快检测频率；还不够就只覆盖赶得上的比赛，并在网站上如实标注 |
| 解析器跟不上最新补丁，解析失败 | M0 必须用最新补丁的比赛测试。失败时评估改用 clarity 直接解析；或者评估 STRATZ 的接口（需要申请 token，它提供哪些位置数据要先核实） |
| GitHub Actions 跑不动（太慢或内存不够） | 写进 M0 报告，由 Richard 决定是否用付费机器 |
| 存储超出套餐 | 降低位置采样频率，或只保存团战前后的时间窗口 |
| 全部不可行 | M1–M3 取消，M4 照做；小地图保持"示意位置" |
